# Custom view procedure

1. Call prepare_project_custom_view for the current project or preview. Keep dataset_id, revision and access_scope. For previews use custom_view_preview exactly (preview_id, snapshot_key, cache_token). Set include_template=true when the rendering reference/template is needed; evidence-only preparation stays concise.
2. For an existing view, recover its content, custom_view_id and expected_version with list_project_custom_views/read_project_custom_view. Keep the existing workspace visible during revision; use open_project_custom_view only when the user asks to display an already-saved view. Revisions update that view; an explicitly requested copy creates another.
3. Use authorized table data, user-provided content, or registered trial/document evidence. Gather table data with read_project/read_project_preview, not workspace navigation. Paid reads allow limit 1–100; prefer 100 for broad counts, follow next_offset, and honor the free first-ten boundary. Retrieve profiles/documents with the evidence skill where needed. Keep source_ids and follow all document parts for complete retrieval.
4. Call save_project_custom_view with title, original query, summary (empty allowed), html, dataset_id, revision, source_ids and request_key. Set artifact_kind for the output and evidence_basis for its actual source: trial_evidence requires registered sources; project_tables/user_provided allow an empty list. Use renderer=interactive for any custom CSS (style blocks or style attributes), styled cards, CSS-based charts, controls or scripts, even when the view has no interaction or JavaScript. Reserve renderer=static for the supported semantic HTML/SVG shell without custom CSS.
5. Revisions pass custom_view_id and expected_version and a fresh request_key. Identical retries retain the original key and payload. REPORT_VERSION_CHANGED requires reading the latest view and reconciling the requested edit. A changed project context requires fresh prepare_project_custom_view and evidence reconciliation. Recovery details identify whether the retained save is retryable or needs correction.
6. The save result opens Custom views; do not add a redundant open call after success. custom_view_saved=true means read-back verified storage. Guest storage is temporary; account connection attaches the project and views. If presentation_status=unavailable after verified storage, open the saved view with presentation_recovery; do not repeat the save. On save failure, the draft remains retained server-side and a recovery control appears beside the unchanged workspace. Use retry_project_custom_view with retry_id for the retained payload; retention lasts up to 30 minutes in this server session. If it expired, reuse the original content.

## Static renderer
On STATIC_RENDERER_CUSTOM_CSS, the save was rejected before persistence because static mode would discard styling. Resubmit the complete self-contained HTML with renderer=interactive and a fresh request_key, or rebuild using the supported static shell. Preserve the existing view ID/version when revising. Do not retry the unchanged payload or remove styles merely to pass validation. External stylesheets must be replaced with inline CSS; neither renderer can load network assets.

Use semantic HTML and the shell’s supported classes: main/section, h1–h3, p, figure/figcaption, .table-scroll, .bar-chart, .bar-row, .bar-label, .bar-track and .bar-value. Bar tracks use SVG rectangles with viewBox="0 0 100 12" and preserveAspectRatio="none"; labels stay in HTML at a stable size. Other SVG charts use a viewBox sized for their intended display width. Use SVG fill/stroke attributes for marks and matching legend swatches. Keep a legend inside the same SVG or use labeled HTML bar rows. The server provides CSS; custom CSS/scripts require the interactive renderer. Keep HTML below 800 KB.

## Interactive renderer
Use self-contained inline CSS/JS and addEventListener. The opaque-origin sandbox blocks external assets/network, parent DOM/account access and direct database writes. Use task-appropriate non-patient data.

Existing state bridge: window.TrialAgents.getState() reads saved state; setState(object) updates a local draft. A deliberate host Save changes action persists that draft with ownership/version checks. Stable input/select/textarea IDs or names are tracked in state.form. Custom controls initialize from getState() and call setState on edits; keep JSON under 200 KB. Automatic input saving is not provided. Keep this existing mechanism compatible; ordinary generated tracker content can also be revised through ChatGPT.
